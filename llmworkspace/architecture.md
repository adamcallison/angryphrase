# angryphrase — Architecture

This document describes the system **as it is built**. Where it disagrees with the code, the code wins. It is a map for navigating the codebase, not a specification to implement.

This document is self-contained. Its companion is `llmworkspace/future_considerations.md` — extension points and anticipated future work; the two files are the **live doc set**. Everything else in `llmworkspace/` is working material that comes and goes with the current work — audit records, findings lists, resolution write-ups, scratch analyses — none of it enumerated here, and none of it part of the live set or citable from it. The rules governing the doc set and the citations that may point into it are in §14.

## 1. System Overview

`angryphrase` is a client-only web application for building and solving cryptic-style crossword puzzles. It runs entirely in the browser, persists to `localStorage`, and ships as a single self-contained HTML file via `vite-plugin-singlefile` (all JS/CSS/favicon inlined into `dist/index.html`; no external runtime fetches). There is no backend, no accounts, no multi-user anything.

There are exactly two top-level experiences — **Builder** and **Player** — connected only via puzzle JSON files exported to and imported from the user's file system. In-app routing is a `route: 'landing' | 'build' | 'play'` enum on `AppState` (no router library); the landing page is always shown on load.

Stack: Svelte 5 (runes), TypeScript, Tailwind (build-time only), Vitest. Node ≥ 22 pinned via `.nvmrc`.

## 2. Architectural Principles

Four principles shape the whole codebase:

1. **Thin UI.** The UI layer is as thin as possible. All logic lives in pure logic modules with no knowledge of Svelte, HTML, DOM, or rendering. Components render view-models and invoke action bags — nothing else.
2. **Domain-Driven Design.** The domain model is the centre; persistence, format, and UI are adapters at the edges. Pure functions over immutable domain objects are the unit of behaviour. Reducers never mutate inputs; a small `clone` helper handles the few deep structures (grid). No Immer.
3. **Explicit types.** Data bundles have named types; field types are precise (`Letter | null`, not `string`); illegal states are unrepresentable where feasible (range-checked branded constructors).
4. **No primitive obsession.** `Row`, `Col`, `GridSize`, `Letter`, `PuzzleKey`, `Title`, `Author`, `DisplacedClueId`, `WordLength`, `WordNumber`, `ToastId`, `EpochMs`, `DurationMs`, `CellCoord` are branded types; `Direction` is a discriminated union. Plain `string`/`number` do not appear in domain signatures. One deliberate exception: the `Rng` interface (`domain/rng/Rng.ts`) uses plain `number` (`nextInt(n)`) — branding a count→index operation cascades nonsense.

   **Brand constructors carry one of two contracts, and the name says which.** `try(x)` returns `T | null` and never throws — it is the failure-as-data constructor, used where the input comes from outside the domain (UI input, file parse) and may legitimately be bad. `of(x)` returns `T` and never returns null — it throws `RangeError` when the value is out of range, and is used where the value is derived inside the domain, so a bad value is a bug. A brand with nothing to reject (`Title`, `Author` — any string is valid) exposes only `of`. One brand's constructor is **grid-scoped**: `CellCoord` (a `{ row, col }` pair proven in-bounds for the grid that minted it) has no local `try`/`of` at all — its only minter is `Grid.tryCoord(g, r, c)`, because its rejection condition is relational to a runtime grid. `domain/grid/CellCoord.ts` exports the type only; `Grid` owns the mint.

### Layer 1 — `src/builder/state/`, `src/player/state/`, `src/app/state/` (pure reducers)

Each module publishes its API at the folder root (`state.ts`, `intents.ts`, `reducer.ts`; `app/state/` additionally `effects.ts`) and keeps implementation helpers under its own `internal/` subfolder. All three import `domain/` freely.

Module boundary rules (ESLint-enforced):

- `app/state` is a client of the other two: it imports their **root files only** (value and type), never their `internal/` files.
- `builder/state` and `player/state` do **not** import each other at all — no path resolving into the sibling `state/` tree is allowed. Shared concepts (e.g. `Cursor`, `GridInteraction` and its shared intent payload variants `GridInteractionIntent`) live in `domain/`. Both `intents.ts` files define their unions using the shared payload variants for the six shared kinds (`select-cell`, `move-cursor`, `type-letter`, `backspace`, `escape`, `click-clue-panel-word`); the six grid-interaction kinds and the two `report-*` failure kinds (`report-import-read-failure`, `report-pick-failure`) therefore appear with the same `kind` string in both unions. (`browse-clue-panel-word`'s payload also lives in `GridInteraction` with the other shared payload variants, but the kind itself is Player-only — see the Focus section.) To make routing unambiguous, every Builder/Player intent variant carries a `target: 'builder' | 'player'` literal discriminator, spelled inline in each union member. Each `intents.ts` additionally exports the named per-kind handler types `BuilderIntentOf<K>` / `PlayerIntentOf<K>` (`Extract` over the union by `kind`, used by every internal handler signature) and `BuilderIntentMinusTarget` / `PlayerIntentMinusTarget` (the union minus `target`, consumed by the facades' curried dispatchers, §5); the private one-line `DistributiveOmit` idiom each alias is built on is defined unexported in each `intents.ts`. `ConfirmableIntent` carries `target` too. Routing is by discriminator, not by kind string; see §5.
- Neither imports `app/state` (no cycles).
- Tests import from `internal/` freely; the rule constrains only cross-module imports within `src/`.

`builder/state/internal/` contains `designMode.ts` (design-mode intents + reconciliation orchestration), `fillMode.ts` (thin policy adapters over `GridInteraction` for the typing/cursor intents — gating on `mode`, the `answerLetter` slot — plus markers, clue edits, metadata), `joinSubMode.ts`, `reattachSubMode.ts`, `importExport.ts`, `lifecycle.ts` (reset), `reconcileWords.ts` (the reconciliation algorithm).

`player/state/internal/` contains `solving.ts` (thin policy adapters over `GridInteraction` — gating on `phase`, the `playerLetter` slot, plus the private `applyCursorChange` fold that owns the check-clear and anagram re-eval rules for all five cursor-changing intents — plus check, clear-errors), `lifecycle.ts` (import flows, reset, apply-loaded-progress), `anagram.ts`.

### Layer 4 — `src/ports/` (side-effect implementations)

| Module | Implements | Wraps |
|---|---|---|
| `ports/localStoragePort.ts` | `StoragePort` | `window.localStorage` |
| `ports/downloadPort.ts` | `DownloadPort` | `URL.createObjectURL` + `<a download>` click |
| `ports/filePickPort.ts` | `FilePickPort` | `<input type="file">` (listens to `change` *and* `cancel`) + drag-and-drop |
| `ports/rngPort.ts` | `Rng` | `Math.random` (production; tests use seeded Mulberry32) |

Port contract:

- Port implementations are **stateless** — every method is self-contained over per-call locals; the module-level `export const xPort` instances are benign stateless singletons.
- **Never-throw:** `StoragePort`/`FilePickPort` methods never throw; non-`Error` throws are coerced to `Error` at the port boundary.
- **Storage reads** return `LoadResult<T>`:

  ```ts
  type LoadResult<T> =
    | { kind: 'loaded'; value: T }    // bytes successfully read
    | { kind: 'absent' }              // nothing stored under this key — silent
    | { kind: 'failed'; error: Error }; // the underlying primitive threw
  ```

  The failure signal travels in the type, so the contract is enforced at compile time. The port implementation warns **once on `kind: 'failed'`**; callers do not warn on load and never try/catch. `absent` and `failed` both collapse to a "fresh-start" / "drop-the-key" response at the call site today — main.ts returns `AppState.blank(...)`, `appStore.handleLoadPlayerProgress` returns `null`. The three cases stay distinguishable in the union so a future port that surfaces a meaningful difference (e.g. quota-exceeded vs. missing) does not require another breaking change. `LoadResult<T>` is defined in `src/domain/ports/ports.ts` and is used by both `StoragePort.loadBuilder()` and `StoragePort.loadPlayerProgress(key)`.

- **Storage writes** return `Error | null` silently — the appStore (which has dispatch context) `console.warn`s each failure and dispatches `report-builder-save-result { ok }` / `report-player-save-result { ok }` (`src/ui/bindings/appStore.svelte.ts`). The reducer turns the result into the `builderSaveFailed` / `playerSaveFailed` state flags; the persistent SaveFailureBanner derives from them (§8). No toast, no latch, no cadence — a persistent condition gets a persistent signal.
- **File picks** return discriminated unions carrying `Error`: `PickResult` = `'picked' | 'cancelled' | 'failed'`; `DroppedFileResult` = `'read' | 'failed'` (a drop has no cancel path). Cancel is fully silent; failures travel as data and the facades warn once + dispatch the failure intent.
- Consumers add no redundant catch layers — callers pattern-match the result union, they do not catch. The type makes both contracts (`LoadResult<T>` and `Error | null`) the only visible failure channels; if a caller needs to react to a load failure it does so via the union, and if it needs to surface a save failure it dispatches `report-builder-save-result` / `report-player-save-result` from the write-result callback. A defensive try/catch around a port call indicates a port author broke the contract, not that the consumer needs another guard.

### Layer 5 — `src/main.ts` (the only composer)

Boots the app: instantiates production ports, builds `deps = { rng: rngPort, now: () => EpochMs.of(Date.now()) }` and `ports = { storage, download, filePick }`, calls `createInitialAppState(ports, deps)` (the bindings-layer boot function) then `createAppStore(initial, deps, ports)` exactly once (running on default options: 400 ms persistence debounce), calls `installTeardown(store)` (registers the `pagehide` listener — see `teardown.ts`), and mounts `<App appStore={store} />` to `#app`. Nothing else constructs an `AppStore` in production; nothing else registers a `pagehide` listener. `main.ts` holds no domain knowledge — the `BuilderState` reload shape, the `AppState.blank(...)` fallback, and the persistence-teardown wiring all live in `ui/bindings/`.

## 4. Boundary Enforcement

The layer matrix is declared once, in `tools/boundaries.js`, and enforced by ESLint: `eslint.config.js` imports that spec and generates its boundary rules from it. `tsc` does not check paths.

Two properties of the enforcement:

- **Allowlist, not denylist.** Each layer may import only what the spec grants it, so an unanticipated target — `src/main.ts`, a non-root file of a sibling state module, a deep path into another layer — is blocked by default instead of slipping past a list of forbidden prefixes.
- **Path-resolved.** Each import specifier is resolved to the repo-relative file it denotes before matching, so relative spellings, extensions and `./`-style forms cannot dodge a rule.

Every source file belongs to exactly one layer: a file that matches no layer, or more than one, is reported. Ambient `*.d.ts` declaration files are exempt — they declare, they do not import at runtime.

| Source path | May import | Blocked |
|---|---|---|
| `src/domain/**` | sibling `domain/**` files only | `svelte`, DOM globals, `src/ui/**`, `src/ports/**`, all three `state/` trees, `src/main.ts`; `domain/brand` except the branded-type owner modules |
| `src/builder/state/**`, `src/player/state/**` | `domain/**`, own module (incl. own `internal/`) | each other (fully), `svelte`, DOM globals, `ui/**`, `ports/**`, `app/state/**`, sibling `internal/**`, `domain/brand` |
| `src/app/state/**` | `domain/**`, the public root files (`state.ts`, `intents.ts`, `reducer.ts`) of the other two state modules, own siblings | `svelte`, DOM globals, `ui/**`, `ports/**`, the other modules' `internal/**` and any other file of theirs, `domain/brand` |
| `src/ui/**` (except `ui/bindings/**`) | siblings; **type-only** from `ui/bindings/**` and `domain/**`; `App.svelte` alone may import bindings **values** | value imports from bindings, `ports/**`, all `state/**`, `domain/brand` |
| `src/ui/bindings/**` | all of `src/**` | `domain/brand` |
| `src/ports/**` | `domain/ports/ports.ts`, `domain/rng/Rng.ts`, `domain/puzzle/PuzzleKey.ts` | everything else, `svelte`, `domain/brand` |

**Brand ban.** `domain/brand` is the branding-primitive module — the unsound `brand()` escaper that bypasses range-checked constructors, and the checked `intBrand()` factory that supplies them. It is importable only by the branded-type owner modules — 15 as of 2026-11-13: the original 13 plus `domain/grid/CellCoord.ts` (owns the `CellCoord` type; type-only `Brand` import) and `domain/grid/Grid.ts` (owns the `CellCoord` mint — `Grid.tryCoord` wraps via the escaper after its bounds check; `Grid.ts`'s owner status covers only this — it holds no lint exception of any kind; non-null assertions are banned absolutely repo-wide, per the 2026-11-19 zero-suppression decision). The owner set lives in `tools/boundaries.js`; it is not duplicated here, and the boundary self-test checks it against the repository in both directions. `test/**` is out of scope (tests legitimately need the escaper for edge-case fixtures).

**DOM globals.** `domain/**` and the three state trees may not reference browser globals (`window`, `document`, `localStorage`, `sessionStorage`, `navigator`, `location`, `history`, `fetch`, `globalThis`). The bindings layer, the UI layer and the ports may.

**Dynamic import.** `import()` is banned outright in `domain/**` and the three state trees; elsewhere it is subject to the same matrix as a static import.

**Self-verification.** `test/boundary/imports.test.ts` drives the ESLint `Linter` API over fixture strings (with `filename` set so the per-glob rules apply) and asserts that every forbidden edge is rejected **by the expected rule** — static import, dynamic `import()`, DOM-global reference, brand import, unlayered file — while every allowed edge passes. `test/tools/boundaries.test.ts` checks the spec module's own integrity: areas and layers resolve to real paths, brand owners exist, are unique and really import `domain/brand`, and the shipped spec validates.

**Cycle policy.** `domain/` modules import each other acyclically (`domain/format/` is the bottom). No cycle can cross the bindings seam because state reducers cannot import `ui/` or `ports/`; `madge --circular` runs in `npm run lint` as a backstop.

## 5. Communication Patterns

**UI → logic.** Leaves invoke typed action-bag props. The facade-implemented bag functions construct the typed intents — branded fields via the domain constructors (`Grid.tryCoord` for click coordinates — the only way a `CellCoord` enters an intent, checked against the grid the facade reads from the store; `Letter.try`, `GridSize.try`, `Title.of`, `Author.of` for the rest), which only bindings may call. Every one of those constructors is total — none of them throws: a `try`/`tryCoord` yields `null` on invalid input, and the action then does nothing; an `of` has no invalid input to reject. An action that must tell the caller what it accepted returns the outcome — `changeGridSize(size: number): boolean` reports whether the size was taken; on rejection the facade raises the failure report (an app-level `report-*` intent, which the app reducer turns into a toast carrying the domain's message) and the control restores the authoritative value. Intents are data at the dispatch seam, not callbacks. Components never call reducers and never construct branded values.

**Logic → UI.** Leaf-shaped, serializable, plain-typed view-models, derived reactively (Svelte 5 `$derived`) in `ui/bindings` from `AppState`.

**Reducers → effects.** Every reducer has the signature `(state, intent, deps) → { state, events: DomainEvent[] }` and is pure. Reducers compute the next state plus a *description* of side effects as data; they perform nothing. `deps = { rng: Rng; now: () => EpochMs }` is injected at dispatch; most cases ignore it. The cases that use it: design-mode toggle (`reconcileWords` mints `DisplacedClueId`s), `confirm-reset-builder` (`PuzzleKey.generate`), `anagram-scramble` (`Anagram.scramble`), and the app-level toast fold (`Toast.create`).

**`DomainEvent` variants.** State-affecting (consumed by `reduceApp` itself): `toast`, `modal-request`. Bindings-performed: `load-player-progress { key }`, `download { filename, content }`, `clear-builder-storage`, `clear-player-storage { key }`. A `modal-request` always carries its `confirmIntent`, and every one is minted by `confirmEvent` (`domain/notifications/Event.ts`) — no call site builds the literal by hand.

**`reduceApp` returns raw events.** `reduceApp` is the only function that sees all of `AppState`. It handles the seven `AppIntent` kinds directly (`navigate`, `cancel-modal`, `dismiss-toast`, the two `report-*-failure` kinds which return toast events with state unchanged, and the two `report-*-save-result` kinds which flip the §8 save-failure flags — no-ops when the flag already matches). For Builder/Player intents it invokes the sub-reducer (forwarding `deps`), composes the resulting `AppState` by swapping the sub-slice into `state.builder`/`state.player`, and returns the sub-reducer's events *raw* — the `toast`/`modal-request`/external events flow up untouched. `reduceApp` does not touch `state.modal` / `state.pendingConfirmIntent`; modal lifecycle is the bindings layer's responsibility (see `Confirmation modals as state` below). **`applyEventsToApp` is not called in `reducer.ts`; folding is the store's job.**

**Routing.** After the `AppIntent` switch, `reduceApp` switches on `intent.target` to invoke `reduceBuilder` (for `target: 'builder'`) or `reducePlayer` (for `target: 'player'`), composing the sub-slice swap inline. The switch is exhaustive, and a post-switch `throw` (where `intent` has narrowed to `never`, so no cast) preserves the unknown-target guard — pinned by a reducer test. No `AMBIGUOUS_INTENT_KINDS` set exists, and there is no route-based fallback; an ambiguous dispatch cannot occur because the discriminator resolves at the dispatch site. Each experience facade stamps the correct `target` literal through one curried dispatcher per facade (`d(partial)` spreading `{ target: 'builder' | 'player', ...partial }` over the `*IntentMinusTarget` union) — the single owner of the literal per facade, fully type-checked at every call site — and the shared factory helpers `createGridActions` / `createFilePickActions` take a `target` parameter so the grid-interaction and failure intents carry the caller's experience. No runtime intent-kind set is exported: `BUILDER_INTENT_KINDS` / `PLAYER_INTENT_KINDS` — and, earlier, `CONFIRMABLE_INTENT_KINDS` and `AMBIGUOUS_INTENT_KINDS` — are gone. Every guarantee they carried is compile-time: the reducer switches are exhaustive over the intent unions (`assertUnreachable`), and the `target` literal is enforced by the union and the `reduceApp` routing switch (a variant whose `target` is missing or wrong-valued does not compile).

**The `AppStore` is the sole event interpreter and performer of external side effects.** Its `dispatch` is a work-queue loop (reentrant dispatches queue, they do not recurse): `reduceApp` returns `{ state, events }` (raw events) → `applyEventsToApp` fold (the single fold site — `toast` events append to `state.toasts` via `Toast.create(deps.rng, …, deps.now)`; `modal-request` sets `state.modal` / `state.pendingConfirmIntent`; external events pass through) → set the rune (reactive VM updates) → iterate leftover external events. Per event: `download` → `ports.download.download(...)` (an `Error` return dispatches `report-download-failure`, which becomes an error toast); `clear-builder-storage` / `clear-player-storage` → the scheduler's synchronous clears (cancelling pending saves) → `storagePort.clear*`; `load-player-progress { key }` → `storagePort.loadPlayerProgress(key)`, parse the blob if present, dispatch `apply-loaded-progress`. Follow-up intents produced by external events re-enter the queue.

**Toasts as state.** Toasts live in `AppState.toasts`, appended by the fold from `toast` events and removed by `dismiss-toast` intents (auto-dismiss timeout or user click, via `ToastHostActions.dismiss`). There is no imperative `showToast()` anywhere.

**Confirmation modals as state.** `AppState.modal: ModalRequest | null` + `AppState.pendingConfirmIntent: ConfirmableIntent | null`, set by the fold from `modal-request` events. `Modal.svelte`'s Confirm button invokes `ModalActions.confirm()` which dispatches `pendingConfirmIntent` (a `confirm-*` intent) directly; Cancel/Escape dispatch `cancel-modal`. There is no `confirm-modal` intent. While a modal is open, other guarded controls are disabled to avoid stacking. Modal closing happens in the bindings layer's dispatch loop (the `AppStore` work-queue): after `applyEventsToApp` folds each dispatch's events, the loop snapshots whether a modal was open before the dispatch and, if so, clears both fields. Because the UI invariant guarantees the only legal dispatches with a modal open are `cancel-modal` and the modal's stashed confirm intent, this rule is structural rather than a kind-set membership check — no `CONFIRMABLE_INTENT_KINDS` set is consulted.

## 6. Store Construction & Injection

One real store, four experience facades, all factories:

```ts
export type AppDeps  = { rng: Rng; now: () => EpochMs };
export type AppPorts = { storage: StoragePort; download: DownloadPort; filePick: FilePickPort };

export type AppStore = {
  getRoute(); getToasts(); getModal();
  getPendingConfirmIntent(); getBuilder(); getPlayer();
  getScheduler(); getPorts();
  dispatch(intent: AnyIntent): void;   // AnyIntent = AppIntent | BuilderIntent | PlayerIntent, exported from app/state/intents.ts
};

export function createAppStore(
  initial: AppState,
  deps: AppDeps,
  ports: AppPorts,
  options?: { persistenceDebounceMs?: number },  // default 400
): AppStore;
```

- The `PersistenceScheduler` is constructed **inside** `createAppStore` from `ports.storage` (guaranteeing the scheduler's storage is the store's storage) and is never passed in from outside. Its `onWriteResult` reports warn on failure and dispatch the save-result intents (§8).
- The facades are per-instance adapters over an `AppStore`: typed dispatch narrowing, VM getters, `pickFile` (consumes the port's `PickResult`; `'picked'` → returns text, `'cancelled'` → silent `null`, `'failed'` → warn once + dispatch `report-pick-failure`, then `null`), and per-leaf action bags. They own no state and expose no raw-state getter — `AppStore.getBuilder()` / `getPlayer()` are for the bindings layer's own use, and a component sees state only through a view-model. The store itself exposes no whole-state getter either: every read is a named slice (`getRoute` / `getToasts` / `getModal` / `getPendingConfirmIntent` / `getBuilder` / `getPlayer` / `getSaveHealth`), so no consumer can depend on the identity of the state object.

**Prop contract.**

1. `App.svelte` declares `let { appStore }: { appStore: AppStore } = $props()` — the only component importing bindings values. It constructs the four facades and passes each as a prop to its shell; `Modal`/`ToastHost` receive VMs + action bags from the modal/toast facades.
2. Shells declare their facade prop, derive VMs reactively (`$derived(facade.…VM())`), and pass view-model + action-bag props to leaves.
3. Leaves never receive a store or a facade. Each leaf declares exactly the VM(s) + action bag(s) it invokes, e.g. `let { vm, actions }: { vm: BuilderToolbarVM; actions: BuilderToolbarActions } = $props();`. Fieldless intents (`{ kind: 'export-incomplete' }`) are wrapped as zero-arg bag functions for uniformity.
4. `Landing.svelte` takes `{ actions: LandingActions }` (`{ build(); play() }`). `Header.svelte` is static, store-free. Shared-leaf prop shapes: `Modal` = `{ vm, actions }` (the Confirm button invokes `actions.confirm()`; the facade owns the pending confirm intent, so the component never receives it); `ToastHost` = `{ vms, actions }` (`dismiss(id)` — id is a VM-provided branded value passed through); `FilePicker` = `{ label, pick, onpick, ondropfile }` (fully presentational: no IO, no catch layers; `null` from `pick` is a silent no-op — under the port contract `null` reaches the leaf only for cancel).
5. No `setContext`/`getContext` anywhere — context is a runtime back-channel with the same hidden-dependency problem as bare imports.
6. Autosave is driven by the store (§8): after each dispatch, a slice whose reference changed schedules that slice's debounced save. `App.svelte` holds no persistence logic.
7. Tests construct independent stores per test via the factories — `createAppStore(initial, { rng: SeededRng, now: FakeClock }, { storage: InMemoryStoragePort, … })` — with write failures injected via `InMemoryStoragePort.nextWriteError` (one-shot). No shared singleton, no reset helpers, no import-order sensitivity; multi-instance mounting works because no module-level state exists anywhere in the chain.

### Focus (typing focus is a reducer-minted fact)

The hidden typing input is the app's single grid-typing surface. Which interactions hand focus to it is **not** derivable from "the cursor moved" — the pre-2026-11-21 effect refocused on every cursor-field read, which (verified empirically in a real Chrome) re-runs on *every unrelated state change* (a clue-edit commit, a toast) with byte-identical cursor values, yanking focus from whatever the user was doing (the former Tab "cycle" bug). The reducer now owns the decision as `typingFocusSeq`, a monotonic counter:

- Bumped by pointer/activation intents that mean "go there and type": Builder fill-mode `select-cell`; `click-clue-panel-word` / `click-grid-word` in the `subMode none` branch ONLY (a join/reattach click resolves the sub-mode — it is not a typing gesture); Player `select-cell` and `click-clue-panel-word`.
- NOT bumped by anything else — notably `move-cursor`/`type-letter`/`backspace` (the user is already typing; the surface already holds focus), `edit-clue` (typing focus would fight the clue editor mid-Tab-walk), `browse-clue-panel-word` (focus stays in the listbox), toolbar intents (`check`, `clear-errors`, markers, export — focus conventionally stays on the clicked control; re-entry to typing is the Tab stop on the hidden input, or any grid/clue click).

`GridVM.typingFocusSeq` carries the counter to the shell; `TypingSurface`'s `$effect` focuses when it (or `enabled`) *actually changes*, guarded by a last-applied comparison because Svelte 5 re-runs the effect on parent re-render even with unchanged primitive props (empirically verified). After a non-minting click (e.g. Player Check), arrows/Escape/Enter/Tab still go nowhere until the user re-enters typing (Tab to the labelled hidden input, or click the grid / a clue) — but letters and Backspace are grid-first (next paragraph), so typing resumes immediately anywhere.

**Grid-first key routing (focus-model round, 2026-11-21).** Letters and Backspace are grid-bound whenever no other surface owns them: `TypingSurface` mounts a window keydown fallback router (effect-gated on `enabled`; OverlayDialog's effect-gated window listener is the precedent) that routes `/^[a-zA-Z]$/` and `Backspace` to the bag when the event target is neither editable (input/textarea/select/contenteditable — the hidden input itself included, so no double dispatch: its own handler has already routed) nor inside an open dialog (`closest('[role="dialog"]')` — covers the confirm modal and the anagram modal), and no Ctrl/Meta/Alt modifier is held. Everything else — arrows, Escape, Enter, Tab — is untouched: the clue listbox keeps its arrow browsing, dialogs keep their traps, and DOM focus never moves (the A6 ring stays on the clicked control; a letter typed with focus on a toolbar button lands in the grid without focus theft — human decision, letters+Backspace only, over the all-keys+focus-capture form which would hijack listbox browsing after one letter). No new state: the router dispatches existing intents through the existing bag, exactly as the input's own keydown handler does — the E2 leaf-owns-keyboard-normalisation pattern extended from the input's events to the window's.

**Tab-out (Builder, same round).** Tab from the typing surface in the Builder lands in the selected clue row's editor: `TypingSurface` takes an optional `onTabOut(): boolean` — plain Tab (never Shift+Tab, the backward walk stays default) offers the callback the key, and a `true` return means focus was moved and the default walk is prevented; absent/false falls through to normal Tab order. `BuilderCluePanel` registers its handler with the shell and focuses the input of the row whose id is the panel VM's `highlightedId` (no new state — the clicked row is already state-known; rows without editors return false and the default walk runs). Clicking a Builder clue row still means select-and-type: the mint is unchanged. Human decision on record, over the alternative of focusing the editor on row click, which would break the select-and-type contract.

**Keyboard-focus indicator (same round).** `TypingSurface` tracks last interaction modality via window `pointerdown`/`keydown` capture listeners (effect-gated on `enabled`) and reports up via an optional `onTypingFocusChange(keyboard: boolean)` — true on input focus when the last modality was keyboard, false on blur and on unmount (covers route/phase switches that unmount the surface without firing blur). The consumer is `ui/shared/GridTypingBlock.svelte` — the wrapper div + `Grid` + `TypingSurface` extracted as one leaf, so the shells stay pure (composition only: `$derived` VMs and dispatch). The block holds the modality boolean as its own local `$state` and toggles `.focus-ring-within` on its wrapper: the A6 ring values (solid, 2px, offset 2px, `primary`) applied unconditionally by the class, because the keyboard/pointer decision is made in JS, not CSS — pure-CSS forms (`focus-within`, `:has(:focus-visible)`) fire on pointer mints too (verified empirically in a real Chrome). Human decision B2, recorded honestly: B1 (the boolean as the first-ever shell-local `$state`) was the initial pick and landed first; the human re-opened it the same day on pattern-purity grounds and chose the leaf — the flip was cheap precisely because the round's remaining dispatches had not landed. The `CluePanelShell` precedent applies: shared chrome goes to a leaf when it is a genuine ownership boundary, and "the grid has your typing focus" is a fact of the grid-typing block, not of either shell. Touch taps keep the yellow cursor as indicator (`pointerdown` suppresses the ring, convention-consistent). The hidden input itself stays ringless; the ring encodes "the grid has your typing focus", not "this element is focused". Grid-first router letters never ring (focus never enters the input).

**Boundary rule (why this is a state fact, not a display concern).** State records facts about the session's interaction that *any* consumer — DOM or headless — could act on (`cursor`, `subMode`, `checkResult`, `typingFocusSeq`: "the user just made a go-there-and-type gesture" is true for a voice client or a test harness, no pixels required). State never records facts about a particular rendering of them (`scrollY`, "toast-is-visible", flash timers fail this test — a headless consumer could not act on them — and stay out). `typingFocusSeq` sits in the `cursor` family: a reducer-witnessed interaction fact whose only current consumer happens to be a `focus()` call. It is not an exception to §9 — nothing renders it — and naming it by DOM vocabulary ("focus") is a naming convenience, not a layer placement. The focus-model round's router, Tab-out hook and modality gate are display-layer DOM behaviour dispatching existing intents through the existing bag — they add no state surface, and `typingFocusSeq` remains the only focus fact state records.

### Guarded actions (request/confirm pairs)

Four user actions are guarded: switch-to-design, Builder import, Builder reset, Player reset. Each is two intent variants: `request-*` checks the guard — blank state executes directly, non-blank state returns state unchanged plus a `modal-request` event carrying the matching `confirmIntent` — and `confirm-*` (dispatched by the modal's Confirm button) executes unconditionally in the state it was granted from; the Player reset confirm is pinned to no-op outside the solving phase (`lifecycle.ts` phase guard, pinned `lifecycle.test.ts`: "confirm-reset-player: import phase is no-op (defensive)"). The three Builder `confirm-*` handlers are genuinely unconditional. No `force` flag; no reducer ever refuses and re-fires.

### Polysemous click intents

`click-clue-panel-word` / `click-grid-word` branch on `state.subMode`:

- `none` → navigate the cursor to the word's start cell and set direction, and bump `typingFocusSeq` (this is a "go there and type" gesture — see the Focus section).
- `join { source }` → attempt the join. Validity: source ≠ target, source has no outgoing `nextWord`, target not already pointed to, both exist. On success: set `source.nextWord`, displace a non-empty target clue to the displaced list, materialize the default space boundary marker on the source's last cell if the direction pair there is empty, reset sub-mode. On failure: toast with reason, sub-mode stays active.
- `reattach { displacedClueId }` → attempt reattach. Validity: target exists, empty clue, is a chain head. On success: move the clue text, remove the displaced entry. Only text transfers, never chain membership.

`unjoin` clears `source.nextWord` **and** its chain-boundary marker pair, and blanks the downstream word's clue — displacing it into the displaced-clue list first if it was non-empty (the same policy as join; a no-op under normal invariants, data-preserving in imported edge states). The boundary-marker reads/writes for join/unjoin go through `ChainMarker` in `domain/chain/` (`materializeDefaultBoundary` / `writeBoundarySeparator`). Admission rules for both join (`source has no nextWord`, `target not already linked`) and reattach (`target clue empty`, `target is a chain head`) are owned by `ChainAdmission` in `domain/chain/`, and user-facing rejection messages come from `ChainAdmission.message(result)`. `escape` cancels join/reattach sub-mode (Builder) or closes the anagram modal (Player).

### Reconciliation (design-mode grid changes)

`toggle-design-cell` runs `reconcileWords` (`builder/state/internal/reconcileWords.ts`), which reconciles the previous `Word[]` with words re-derived from the toggled grid: survivors keep clue/`nextWord` (length changes are toasted as "Word N Direction was shortened/lengthened"); destroyed words with non-empty clues become `DisplacedClue`s; links to destroyed words are cleared and downstream "See N Direction" clues are emptied; new words appear blank. It also maintains the chain-boundary markers on the grid — markers on linked words' old end cells move to their new last cells when links survive (preserving the user's space/hyphen/none choice), clear when links sever or the source word is destroyed, and default to space when the old end cell itself was destroyed; markers on standalone words' cells are user data and are never touched. The read/write mechanics go through `ChainMarker` (`domain/chain/`); the *policy* — which marker moves where and when — stays in `reconcileWords`. Finally it runs `Numbering.assign` and `ChainValidation.validate` as a safety net — any post-reconciliation violation throws (an invariant breach is a bug, not a user-facing condition). The full edge-case suite lives in `test/builder/state/internal/reconcileWords.test.ts`.

### Player specifics

- **Check clear-on-change:** an interaction that changes the grid or cursor sets `checkResult = null`; a no-op interaction (out-of-bounds or unselectable click, same-cell re-click with no direction toggle, blocked move, backspace with nothing to clear) leaves state untouched. Implemented once in the `solving.ts` adapters over `GridInteraction` outcomes, in the private `applyCursorChange` fold shared by all five cursor-changing intents — a `null` outcome means state unchanged (same reference), a non-null outcome means grid and/or cursor changed. The check result drives the toolbar message/colour and the `clear-errors` action (`incorrectCells`), never per-cell grid colouring.
- **Anagram helper:** `open-anagram-helper` requires a cursor on a word and records `openedForWord`; when the selected word changes away from it, the modal auto-closes. `anagram-input` carries the **raw** typed text; the reducer sanitises it with `Anagram.sanitizeInput(raw, totalLength)` (A–Z only, uppercased, clamped to the chain's letter count) and stores the sanitised string — that sanitised string is what the view-model shows, so the modal never normalises input itself. `anagram-scramble` calls `Anagram.scramble(entries, input, deps.rng)` directly (Fisher–Yates over the non-fixed letters after fixed letters claim from the input pool) and stores the entries-aligned result. The `pool[k]`/`pool[j]` bounds reads inside `scramble`'s Fisher–Yates loop are the codebase's **only sanctioned redundant-guard site**: compiler-forced (`noUncheckedIndexedAccess` types every indexed read `T | undefined`) and provably dead at runtime (the loop bound `i < pool.length - 1` bounds `k`, and `rng.nextInt(pool.length - i)` bounds `j`); non-null assertions are banned absolutely, so the guards stay. Do not convert to `!` or delete without amending this section. No grid write-back.
- **Import flow:** `import-puzzle` accepts complete files only; rejects set `lastImportError` (rendered inline on the import screen) and emit a toast. Success sets the solving phase and emits `load-player-progress { key }`; the appStore loads the saved progress blob, decodes it via `parsePlayerProgress` — which rejects the blob whole unless `playerLetters` is exactly `gridSize` rows of `gridSize` cells (a dimension-invalid blob is corruption or tampering, never the app's own write; it lands on the existing corrupt-blob path: warn, no dispatch, state unchanged) — and dispatches `apply-loaded-progress`, whose reducer applies the letters only if `savedGridSize` matches, only on white cells. The reducer carries no dimension defence of its own (see §8).
- **Builder import** (`request/confirm-import-puzzle`) accepts both incomplete and complete files; success replaces `BuilderState` (imported puzzle + displaced clues, auto-switched `mode = 'fill'`, `cursor = null`); failure toasts the parse errors and changes nothing. `export-incomplete` emits a `download` event unconditionally; `export-complete` runs `CompletenessCheck` first and toasts violations instead of downloading (the gate includes the non-head-clue rule, so the app can never emit a complete file its own parser rejects). On success with displaced clues present, the download is additionally accompanied by a `warning` toast stating how many were omitted and that they remain in the Displaced Clues panel — displaced clues never block export (Builder-only concept, preserved in Builder state and the incomplete format). Filenames come from `Filename.incomplete/complete(key)`.

## 8. Persistence

Two mechanisms, both bindings-layer:

1. **Autosave (dispatch-driven).** The `AppStore` owns autosave: after each dispatch it compares the builder and player slice references with the ones it started that dispatch from, and schedules a debounced save (default 400 ms) for each slice that changed — one timer per slice, so a builder keystroke does not re-arm the player's timer. The scheduler is the internally-constructed `PersistenceScheduler`; the component layer holds no persistence logic. **Behaviour change:** nothing is written at boot — a session writes its first snapshot only after the first change to that slice, so a blank builder snapshot is no longer written on mount. Saves are scheduled *before* the leftover external events are performed, so a `clear-builder-storage` / `clear-player-storage` event cancels the pending save deterministically. The persisted blobs (`persistenceCodec.ts`):
   - **Builder snapshot:** `{ version: 1, kind: 'builder-snapshot', puzzle: <incomplete puzzle shape>, mode: 'design'|'fill' }` — a wrapper around the structural shape (`serializeIncompleteShape` produces the embedded portion directly; no JSON-string round-trip between the structural shape and the wrapper). The reload invariants (`subMode: { kind: 'none' }`, `cursor: null`) are owned by `createInitialAppState` (§3 Layer 2 / `boot.ts`); the wrapper does not carry them, so a saved snapshot has no place to drift them.
   - **Player progress:** `{ version: 1, kind: 'player-progress', key, gridSize, playerLetters: (Letter|null)[][] }` — dimension contract: `playerLetters` is exactly `gridSize` rows, each exactly `gridSize` cells long. `parsePlayerProgress` owns this contract and rejects the blob whole otherwise (corrupt-blob path: warn, state unchanged). The reducer (`handleApplyLoadedProgress`) therefore carries no dimension defence — the `Math.min` clamps and the undefined-row skip are gone, and an out-of-dimension array reaching it is a bug that fails loud via `Grid.cellAt`'s `RangeError`. The appStore is the sole minter of `apply-loaded-progress` intents, always through the codec, so the invariant has one construction site.
2. **Event-driven clears.** `clear-builder-storage` / `clear-player-storage { key }` events (emitted by the confirm-reset reducers) trigger the scheduler's synchronous `clear*`, cancelling any pending debounced save before it fires.
3. **Teardown.** `installTeardown(store)` (in `ui/bindings/teardown.ts`, called once by `main.ts`) registers a `pagehide` listener that invokes the scheduler's `flush()`, firing any pending debounced save synchronously before the tab is hidden. `pagehide` (not `beforeunload`) — `pagehide` covers both unload and bfcache-restore transitions and fires reliably on mobile. `flush()` exists for this single caller (and tests); it is not part of the autosave contract.

**Write-failure surfacing (per slice).** The scheduler reports every attempted write (save or clear, including `flush()`) via `onWriteResult(slice, err)`. The appStore's callback warns (`console.warn`, every failed write — the write path itself is silent, the port warns only on load failures) and dispatches `report-builder-save-result { ok: err === null }` / `report-player-save-result { ok: … }`; the reducer sets `builderSaveFailed` / `playerSaveFailed` on failure and clears on success, no-opping when the flag already matches. The user-visible signal is the **persistent `SaveFailureBanner`** (§11 shared table), derived per slice by the facades' `saveBannerVM()` getters from `getSaveHealth()`: it renders while the condition holds — an ephemeral toast plus a 60 s re-toast latch no longer exists (removed 2026-11-21: a persistent condition signalled by an ephemeral, dismissable, missable toast was a data-loss risk; the latch was a symptom — the condition is continuous, the warning was not). The banner is route-scoped by construction: the Builder banner shows on the Builder route, the Player banner on the Player solving route (player writes only happen while solving, so the import screen never needs it). Copy is VM-minted (`saveBannerVM.ts`, §9 home) — state stores booleans only. The flags pass the Focus-section boundary rule: "saving is failing" is a fact any headless consumer could act on; no rendering is recorded. Reminders are no longer needed — the banner does not lapse. A failed Builder clear self-heals on the next successful autosave; a failed player-progress clear leaves a stale keyed blob that resurrects only if that exact puzzle is re-imported (accepted edge, unchanged).

**Corrupt-state recovery.** At boot, an unreadable Builder snapshot is discarded (`console.warn`, no toast) and a fresh blank puzzle with a freshly generated key starts; corrupt player progress is silently dropped and the import screen shows. `createInitialAppState` in `ui/bindings/boot.ts` performs this, not a reducer.

## 9. View-Models & the Component Contract

All VM types live in `ui/bindings/viewmodels/` — one location, no exceptions: plain, leaf-shaped, serializable, no methods, no Svelte. **Display values are plain primitives** — a number shown to the user is a `number`, not a branded domain type — so no component has to unwrap a brand to render it. Branded types remain only where an action call needs the identifier (`WordKey`, `DisplacedClueId`, `ToastId`). `ToastVM` (id, kind, message, `ttlMs` — a plain number; the leaf schedules its own auto-dismiss; `announcement` — the assistive-tech copy minted by the derivation: kind word + message, e.g. "Error: Saving failed", so the colour-only `kind` has a spoken encoding; consumed by ToastHost's live region), `ModalVM` (kind, title, body, confirmLabel, cancelLabel | null), `GridVM`/`GridCellVM` (size, `typingFocusSeq` — the reducer-minted typing-focus counter passed through to the typing surface (Focus section); `cursorAnnouncement` — the compact spoken form of the cursor cell minted by the same derivation (`row R, column C,` + `letter X` / `empty` / `blocked`; deliberately NOT the full `label` grammar — no word/separator/selected clauses, because it fires per keystroke), consumed by `Grid`'s live region; the former `cursorRow`/`cursorCol`/`cursorDirection` fields were removed with it — they existed solely to re-trigger the old focus effect — and cells of `row`, `col`, `black`, `letter`, `number`, `hilite: 'none'|'selected'|'in-word'`, separatorRight/Bottom, selectable — plain values throughout), `BuilderToolbarVM` (mode, grid-size gating, marker flags, completeness gating + violation summary + its spoken join `violationAnnouncement` — summary labels joined `"; "`; the grid-size bounds are the domain's `GridSize.MIN` / `GridSize.MAX`), `ClueEntryVM` (`id` — the stable per-word identifier the leaf uses for DOM refs and keyed lists, derived by the bindings layer from `WordKey.toCanonical`; `number` — a plain number; `direction`, `displayClue`, `lengthPattern`, `selectLabel` — the VM-minted accessible name for the row's select affordance ("Select clue N across/down"), minted unconditionally in `deriveCluePanelVM` (§9 home for display copy; consumed by the Builder panel's underlay button — no DOM ids exist, so `aria-labelledby` is impossible); chain affordances — builder-only fields are simply false in Player), `CluePanelVM` (`across`, `down`, `highlightedId` — the id of the highlighted entry, or null), `DisplacedCluesPanelVM` (always visible, empty state "No displaced clues"), `BuilderSubModeBannerVM`, `BuilderShellVM`, `ActiveClueBannerVM` (`wordNumber` — a plain number or null; always reserved space; null pattern for non-head words; `announcement` — the VM-minted spoken form `N across: clue (pattern)`, consumed by `PlayerShell`'s single speech-mirror region, never by the twice-rendered banner component), `PlayerCluePanelVM`, `PlayerToolbarVM` (canCheck/canClearErrors/canReset/canOpenAnagram/canImportNew), `PlayerCheckResultVM` (classification, incorrect/empty counts, `message` + its spoken `announcement` — message + " (N incorrect)" / " (N empty)" clauses mirroring the visible spans, VM-minted per the same §9 home; consumed by `PlayerToolbar`'s speech mirror), `AnagramModalVM`/`AnagramTileVM` (tiles with fixed/letter and a per-tile `separatorAfter` minted by the derivation — the last tile's own `'none'` case, a missing mid-chain separator a loud contract-drift throw; the template never indexes a separators array, expected letter counts as plain letter strings, input validity, scramble gating; the derivation returns `AnagramModalVM | null` — null = closed, the same convention as `ModalVM`/`AppState.modal`; no zero-filled placeholder view-model for the closed state), `PlayerShellVM` (phase-discriminated: the import variant carries only `importError`; the solving variant carries title, author, grid, banner — a single `ActiveClueBannerVM` rendered both above and below the grid (speech goes through PlayerShell's one speech mirror, so the double render cannot double-announce) — clue panel, toolbar, anagram and check result — the two phases cannot be confused, and no placeholder view-model exists for the import phase), `SaveBannerVM` (2026-11-21: `message` — the per-slice save-failure copy, minted here because the VM layer is display copy's sanctioned home; `deriveSaveBannerVM(failed, slice)` returns null when the slice is healthy, so the banner and its always-mounted speech mirror both key off one value, and no zero-filled placeholder view-model exists for the healthy state).

A component contains no business logic: no imports from `domain/` or any `state/` module, no reducer or domain-function calls, no domain-value computation, no VM mutation. Components compute pure presentation matters from props only (e.g. resolving `hilite` into a Tailwind class, or `PlayerCheckResultVM.classification` into the check-result colour via `PlayerToolbar`'s component-local map — the map is exhaustive and compile-checked against the VM's own `classification` type). A component never sanitises or normalises a value for the logic layer: it dispatches the raw input and renders what the view-model carries back. A component never evaluates a domain rule either: it collects what the user entered, submits it unchanged, and restores the authoritative value when the logic layer rejects it — the rejection is explained by the logic layer (a toast carrying the domain's message), not by the component. No component reads raw state: mode, phase, selection and every other fact a component branches on arrive as view-model fields. The ESLint rules in §4 make the value-import paths compiler-blocked, not convention.

**Snippet convention.** Svelte 5 `{#snippet}` deduplicates presentational markup sharing one component's reactive scope; a child `.svelte` component is extracted only for a genuine ownership boundary. The reference example is `BuilderCluePanel.svelte`'s `{#snippet clueRow(entry)}`, rendered in both the Across and Down `<ul>`s — `PlayerCluePanel.svelte` uses the same `clueRow` idiom for its rows (`clueRow(entry)` — keydown navigation walks `allEntries`, the concatenated across+down list, so arrows cross the section boundary; the §11 grouped-listbox form), so both clue panels dedupe their row markup the same way (section shells stay explicit: two sections, two headings). The panels' shared chrome — the scroll container `aside` (`max-w-md`, `max-h-[70vh] overflow-y-auto`), the `<li>` refs record (`bind:this` keyed by canonical id), and the scroll-into-view `$effect` — is owned by `ui/shared/CluePanelShell.svelte` (2026-11-21): each panel embeds it and passes its rows as a children snippet that receives the shell's `liRefs` record; the section/h2/ul shells stay per-panel because they differ semantically (Player's listbox `role="group"` wrappers vs Builder's plain `section`s), and the Builder panel keeps its per-row drafts `SvelteMap`. (No DOM ids, no `getElementById`, no cross-component DOM anywhere.)

## 10. JSON Puzzle Format (v1/v2 family; the app writes v2)

`domain/format/` is split into a structural layer and a JSON-I/O layer, and the **structural shape is the canonical wire shape**. The file format (downloaded `.json`, imported files) and the `localStorage` blob format (builder snapshot) share the structural layer by construction — they can only diverge by diverging `v1.ts` itself.

- `domain/format/v1.ts` — **structural layer**. The single source of truth for "what does a v1/v2 puzzle look like as data": `parsePuzzleShape(parsed: unknown) → Result` (validates both accepted versions; accepts any caller-produced `unknown`), `serializeIncompleteShape(p, clues) → object`, `serializeCompleteShape(p) → object`, `ParseFailure`, `PuzzleFileType`. Operates on structured values end-to-end — no `JSON.parse` / `JSON.stringify` anywhere in this module.
- `domain/format/v1Json.ts` — **JSON I/O adapters**. Thin wrappers that convert between the string form (what browser file APIs give and take) and the structural form: `parsePuzzle(json: string)` delegates to `parsePuzzleShape` after a single `JSON.parse`; a `JSON.parse` failure becomes the existing `ParseFailure` shape (`'File is not valid JSON.'`); `serializeIncomplete(p, clues)` and `serializeComplete(p)` call the structural shape function and `JSON.stringify` the result. `Filename` helper lives here (it is a string-output side effect, not a structural shape).

Versions 1 and 2 share an identical schema; they differ only in the interpretation of an **empty chain-boundary marker pair** on a linked word's last cell — v1 parses normalize it to a space marker (materializing the pre-feature implicit default), v2 preserves it as "no separator". The app writes `version: 2`; v1 files remain readable.

```json
{
  "version": 2,
  "type": "incomplete" | "complete",
  "key": "<UUID v4>",
  "gridSize": 15,
  "title": "...",
  "author": "...",
  "grid": [[ { "black": false, "puzzleLetter": "A" | null,
               "spaceRight": false, "spaceBottom": false,
               "hyphenRight": false, "hyphenBottom": false }, ... ], ...],
  "words": [
    { "startRow": 0, "startCol": 1, "direction": "across",
      "length": 4, "clue": "...",
      "nextWord": { "startRow": 3, "startCol": 0, "direction": "down" } | null }
  ],
  "displacedClues": [ { "id": "<UUID v4>", "clue": "...", "direction": "across" } ]
}
```

Key rules enforced by `parsePuzzle` (strict — the failure list is the contract):

- `version ∈ {1, 2}`; `type ∈ {'incomplete', 'complete'}`. Unknown fields fail (a stray `letter` field is rejected — `puzzleLetter` is the only accepted answer-letter name).
- `gridSize` integer 2..25; grid is `gridSize × gridSize`; missing marker booleans default to `false`; `puzzleLetter` is `null` or single A–Z.
- Words: in-bounds starts, `length ≥ 2`, `nextWord` resolves; `ChainValidation` reports no cycles/branches/dangling/self-refs. `number` is never carried in the file (re-derived via `Numbering.assign`); a `number` field fails. `length` is cross-checked against the grid.
- **Complete:** every white cell has a letter; every chain-head clue non-empty; every non-head chain word's clue empty (strict — non-empty fails, no silent normalization); no `displacedClues` field.
- **Incomplete:** letters may be null, clues may be empty; `displacedClues` is an array of unique valid-UUID entries.
- On any failure: a human-readable error list, no state change.

`puzzles/*.json` — seven canonical sample files (puzzle1–6 + `guardian_bank_holiday_2026-08-29.json`), all `version: 2`, `type: 'complete'`. Neither the app nor the test suite references the directory; it exists purely as a record of the format. Puzzle6 contains one chain; its previously-implicit space boundary was materialized during the v2 reserialization.

## 14. Doc Set & Citation Policy

The **live doc set** is this file and `llmworkspace/future_considerations.md`. **Everything else in `llmworkspace/` is working material, not part of the live set.** The directory is deliberately unenumerated: it holds whatever the current work produces — audit records, findings lists, resolution write-ups, scratch analyses — plus `archive/` for historical material, and its contents change as the work changes. None of it is a citation target, by filename or by finding number.

**No requirement layer.** This project has no specification document and no requirement identifier space. Behavioural rules live in the code that implements them — as code, as comments, and as test names. The `FR-*` / `NFR-*` identifiers from the project's original requirements draft are **retired**: they scaffolded the initial design and are not part of the live doc set. Do not reintroduce them. The same holds for every other identifier minted by an archived document — the archived code-smell log's, the archived design-review notes' — and for any citation of an audit record by its finding number.

**`llmworkspace/archive/` is historical.** It holds material that informed the original design and is kept for reference only. Nothing live may cite it. Archiving a document that a live artefact still cites is a **breaking change to the doc set**: the citation must be re-homed in the same commit.

**Citation rules.** A citation — a comment, a doc comment, or a test title — must resolve to something live:

1. A module, symbol, or path **inside this repository** (e.g. `ChainAdmission`, `domain/grid/WordTopology.ts`). This is the preferred form, and the right one whenever the cited rule is implemented near the citation.
2. A **named section** of this file or of `future_considerations.md` (e.g. `architecture.md §7 (Polysemous click intents)`).

Never cite:

- a path into `llmworkspace/` — the doc set is addressed by document name, never by workspace path;
- a **position**: a line number, with or without a section sign (a `file.ext:` followed by digits, or a `§` followed by three or more digits). Section numbers in this document have at most two digits, so a `§` with three or more digits is a line number;
- an identifier from a retired vocabulary.

These rules are conventions, not compiler-enforced. Comment text is read by people and by agents working on the code, and it is worth keeping resolvable — but nothing depends on it mechanically, so no checker polices it. The project's mechanical checks are reserved for the layer import edges, where a violation actually breaks the architecture. A citation that breaks the rules above is a review finding, not a build failure.
